# Гонка, которую ты докажешь

Индексатор получает пары «путь, число строк». Несколько потоков передают данные в один индексатор. После завершения всех потоков он должен вернуть общее число строк и число файлов каждого расширения. Найдите вход и порядок действий, при которых результат расходится с последовательным подсчётом. Затем исправьте код и измерьте цену исправления.

## 1. Запустите пример

Сделайте свою копию [стартового репозитория](https://github.com/nikitosion/coroutines) и запустите `.\gradlew.bat build` в PowerShell или `./gradlew build` в Linux и macOS. В проекте уже настроены Kotlin 2.4.10, JDK 25, Gradle Wrapper 9.5.1, JUnit 6.1.3 и Lincheck 3.7. В модуле `given/` находится исходный индексатор, в `fixed/` — его копия в другом пакете, в `proof/` — тесты.

Откройте `StarterTest.kt`. Последовательный пример подаёт `A.kt` с тремя строками и `B.kt` с пятью. В результате должно быть восемь строк и два файла с расширением `kt`. Обе версии проходят этот тест. Ещё один короткий тест запускает Lincheck на одном рабочем потоке и проверяет, что инструмент настроен. Дальше вы построите собственную проверку на двух потоках.

## 2. Покажите, где нарушается подсчёт

Прочитайте `given/src/main/kotlin/lab/given/Indexer.kt`. Какие поля меняет `record()`? Какие действия с этими полями выполняют оба потока? Запишите ожидаемый результат для двух записей и предложите порядок выполнения, при котором он может измениться.

Откройте `RaceProofTest.kt` и дополните `defectReproduced(target)`. Для каждого вызова:

1. Внутри `Lincheck.runConcurrentTest { … }` создайте свежий индексатор указанной версии. Запустите два потока, разделяющих этот экземпляр, и передайте им по одной записи.
2. Дождитесь обоих через `join()`, получите `snapshot()` и сравните оба поля с ожидаемой статистикой. Добавьте в вашу проверку узнаваемое сообщение об ошибке с ожидаемыми и фактическими данными.
3. При успешной проверке верните `false`. Если Lincheck предъявил трассу, проверьте по ней, что сработала именно ваша проверка статистики. Только тогда верните `true` и сохраните первую такую трассу. Ошибки настройки, таймауты инструмента и посторонние исключения должны прервать запуск.

Запустите `.\gradlew.bat :proof:raceProof -Pkfd.target=given`. Выберите в трассе строки, на которых расходятся ожидаемый и фактический результаты. Объясните по шагам, что успел прочитать и записать каждый поток. Проверка запускается на уже подготовленных данных в памяти, обращения к диску здесь не нужны.

## 3. Исправьте индексатор и повторите опыт

Оставьте `given/` в стартовом состоянии. Внесите исправление в `fixed/`. Сохраните внешнее поведение и параллельную обработку входных данных. Если выберете общий замок, определите, какие именно действия должны выполняться под ним. При локальном подсчёте определите, кто и в какой момент объединит результаты.

Повторите тот же сценарий с `-Pkfd.target=fixed`. В отдельном обычном тесте проверьте исправленную версию на данных с несколькими расширениями. Сравните с последовательным эталоном и общее число строк, и распределение файлов. У классов результата из разных модулей разные типы, поэтому сравнивайте значения полей.

## 4. Сделайте проверку воспроизводимой

Каркас `raceProof` выполняет 100 повторений в одной JVM. На исходной версии сценарий должен обнаруживать нарушение хотя бы в 90 запусках, на исправленной — пройти все 100. Например:

```text
RACE-PROOF: 94/100 runs failed on given/
RACE-PROOF: 0/100 runs failed on fixed/
```

Первая команда завершается с ошибкой теста, вторая — успешно. Порог 90/100 показывает устойчивость сценария. Даже одной подлинной трассы достаточно, чтобы показать существование дефекта. Обоснование исправления дайте отдельно: почему выбранное средство исключает показанное чередование?

Основной workflow `ci` запускает сборку и обычные тесты при отправке изменений. Когда сценарий готов, запустите отдельно `race-proof` в GitHub Actions через **Run workflow**, выбрав ветку решения. При успешном результате workflow подтвердит ожидаемый отказ исходной версии, проверит обе строки с числом нарушений и успешное завершение исправленной версии.

## 5. Измерьте время и масштабирование

Вход — готовый список пар «путь, число строк», без чтения диска. `200 000 файлов` здесь означает 200 000 элементов. Постройте вход один раз до измерений и используйте его для обеих версий. Полный результат проверяйте по последовательному эталону; генерацию, печать и проверки не включайте в измеряемый участок.


Генератор `makeInput()` уже находится в `proof/src/test/kotlin/lab/proof/BenchmarkInput.kt`. Добавьте рядом `ThroughputTest.kt` со своим замером.

Для этих констант получится 8 частей по 25 000 элементов. При сравнении сохраняйте полный объём данных и для одного, и для восьми рабочих потоков. Одинаковый seed воспроизводит последовательность в одной версии реализации Kotlin; не рассчитывайте на идентичность между произвольными версиями. В одном сравнении используйте один уже построенный вход.

Протокол измерения:

- Сначала проверьте корректность `fixed/`: число строк и распределение по расширениям совпадают с последовательным эталоном.
- Прогрейте оба варианта, затем сохраните не меньше пяти измерений и медиану каждого. Если значения дрейфуют, увеличьте прогрев.
- Для сравнения цены исправления запускайте `given/` и `fixed/` на восьми потоках, на одной машине, с одинаковым входом и JDK. При зависающем `given/` фиксируйте отсутствие завершённого измерения, не придумывайте медиану.
- Для оценки масштабирования дополнительно измерьте `fixed/` на одном потоке с тем же общим объёмом данных. Укажите число доступных процессоров.
- Чередуйте варианты, сохраняйте разброс и описывайте постороннюю нагрузку. Замер можно провести локально или в CI.

Изменение времени: `(t_fixed − t_given) / t_given × 100%`. Плюс означает замедление, минус — ускорение. Для масштабирования отдельно сравните `fixed/` на одном и восьми потоках. Шаблон записи с иллюстративными числами:


```
Условия: [модель CPU и число доступных процессоров], [ОС], [версия JDK].
Вход: 200 000 элементов, SEED=42; генерация вне замера.
Прогрев: 3 запуска; далее 5 измерений, мс:

given/, 8 потоков: 148 141 152 139 145; медиана 145
fixed/, 8 потоков: 131 136 129 158 133; медиана 133

Изменение времени: (133 − 145) / 145 × 100% ≈ −8,3%.
В этой серии fixed/ быстрее; разброс требует осторожного вывода.
fixed/, 1 поток: [свои 5 измерений и медиана].
Масштабирование fixed/: t_1 / t_8 = [свой результат].
```

Восемь программных потоков не гарантируют восемь доступных ядер или ускорение в восемь раз. Если ускорения не получилось, объясните результат через размер работы, конкуренцию, слияние и условия запуска. Зачёт не требует заранее заданного коэффициента ускорения.

## 6. Оформите решение

В README заполните четыре раздела отчёта. Приложите первую трассу с объяснением, две строки `RACE-PROOF`, ссылки на изменённые строки и оба успешных workflow, а также результаты замеров. В `docs/adr-001-concurrency.md` сравните выбранный способ с другим корректным вариантом: какую гарантию даёт каждый, чем он может замедлить обработку и почему вы оставили своё решение. В ADR достаточно сослаться на таблицу из README.
